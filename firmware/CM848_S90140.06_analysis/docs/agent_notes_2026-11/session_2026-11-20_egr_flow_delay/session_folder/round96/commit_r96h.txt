- Seven CM550 functions had rows but no body in the .cpp: the decompiler failed on each with 'Low-level Error: Cannot
  properly adjust input varnodes'. Each takes stack arguments in the compiler's 2-byte-slot layout (a word or byte at
  +4, then a long at +6 ...), which Ghidra's 4-byte-slot default cannot fit, and none had a function_definitions row
  (stack_parameter_layout.csv places parameters only from rows). Full prototypes from the disassembly (each argument's
  load width and offset; round 93's m68k.py) let all seven decompile: cm550_sendCanSingleFrame,
  registerJ1939ReceiveHandler, registerJ1939DiagnosticService, writeJ1939DiagnosticMemoryByParameterId and three
  renamed by what they do:
  - cm550_circularBufferWrite -> cm550_queueEepromByteWrites (the serial EEPROM write queue; its caller's plate already
    called it that),
  - cm550_protectionUpdateHandler -> cm550_updateEngineProtectionRestartLimitationCommands (it writes e2m EPRYO2SO /
    EPRYO2SQ, the restart limitation's shutdown and shutdown-approaching commands, for protection channel 3),
  - cm550_canFrameDataCopy -> cm550_transmitCanFrameOnMessageObject (it loads an 82527 message object and sets TxRqst).
  Their callers now show the arguments: cm550_systemFunction6xParameterized rendered registerJ1939DiagnosticService(1),
  (1, T), (2, T, T) and () with junk stores; it now reads four registrations with the service enum members and the
  handlers. The write-by-parameter-ID handlers show the ID, offset and length they pass.
- The serial EEPROM write queue is one family. Its two rings are typed: eeprom_write_queue_addresses (word[1280] at
  0x80bda8) and eeprom_write_queue_data_bytes (byte[1280] at 0x80c7a8). The only ROM references into
  0x80bda8-0x80cca7 are those two bases (3 users each: the two queue writers and mc68k_runSerialEepromDriverStep, which
  sends each pair to QSM_TR4 / QSM_TR5), and none of the 175 rows that sat inside rendered or was referenced (old
  guesses such as rpm_filter_buffer_start, engine_protection_coolant_ptr_1 and a second circular_buffer_* set); they go.
  The index / count rows are eeprom_write_queue_read_index / _write_index / _count / _last_request_offset (were
  eeprom_circular_buffer_* / circular_buffer_*), and cm550_circularBufferEmptyCheck / cm550_parameterCircularBufferWrite

  it parsed the header as an address. The header is line 1 now and the warning is gone; firmware/CLAUDE.md's bullet that
  called the warning benign is corrected.
